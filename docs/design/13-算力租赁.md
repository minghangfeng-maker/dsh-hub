# 13 算力租赁（按规格、按 10 分钟计费）

> 2026-10-18 立项。用户登录后自己选规格启动 DSH，按时长从积分扣费；积分钱包与模型中转站（12 §6）**共用**——充值一次，既能买机器也能买 token。
> 第一阶段只在 Hub 所在的这台 Linux 主机上跑（把这台机器当作「租了一台云主机」）；远程节点与数据同步是第二阶段（另立文档）。

## 0. 已定决策（用户 2026-10-18）

| # | 决策 |
| --- | --- |
| D1 | 默认三档：2 核 4 GB 0.3 积分/时、4 核 8 GB 0.5、8 核 16 GB 1.0；更高配置「联系管理员定制」（管理员建只对指定用户可见的规格） |
| D2 | 每天登录送积分，**不可累计**：次日发放前，前一天没用完的赠送部分作废 |
| D3 | 计费粒度 **10 分钟**，不足 10 分钟按 10 分钟算（每块开始时预扣） |
| D4 | 余额 ≤ 0 后**宽限 10 分钟**再停机（宽限期不收费），数据保留 |
| D5 | 计费有总开关，默认关；关闭时一切照旧（免费、按 `Quota`） |

**不做（本期）**：在线支付（充值仍由管理员在「钱包」里加积分）、包月、远程节点、在 DSH 页面里弹余额提醒、退款。

## 1. 概念

- **规格（plan）**：`{id, name, cpus, memoryMb, pricePerHourMicro, enabled, userIds, sort}`，存 settings 键 `compute`。`userIds` 非空 = 定制规格，只有名单里的用户能选。
- **块（block）**：10 分钟。每块价格 `blockPrice = ceil(pricePerHour × 10 / 60)`（`computeBlockPriceMicro`）：0.3 → 0.05、0.5 → 0.083334、1.0 → 0.166667。
- **租约（lease）**：一次「从运行到停止」的计费记录，开租时**快照**规格与价格（之后改价、改规格不影响进行中的租约）。每个用户最多一条进行中的租约。
- **钱包**：就是 `relay_wallets`，`balance` 是唯一余额。算力扣费写 `relay_ledger`（type `compute`）；token 扣费仍写 `relay_usage`（不变）。

## 2. 每日赠送（D2）

设置：`RelaySettings.dailyBonusMicro`（默认 0 = 关；建议 0.6 = 2C4G 两小时）。钱包新增两列：

- `daily_bonus_left`：余额中「今日赠送」还没用掉的部分（微积分，≥ 0）；
- `daily_bonus_day`：最近一次发放的日期（Asia/Shanghai，`YYYY-MM-DD`，同 12 §6.5）。

**规则**（全部在 relay 模块的一个函数里，`db.tx` 内完成）：

1. **消费先用赠送**：任何扣费（token 用量、算力块、管理员扣积分）在扣 `balance` 的同一事务里做 `daily_bonus_left = max(0, daily_bonus_left − 金额)`。
2. **作废**（`expireStaleBonus`）：`daily_bonus_day < 今天` 且 `daily_bonus_left > 0` 时，`作废额 = min(daily_bonus_left, max(balance, 0))`；`> 0` 就写一条 `expire` 流水（负数）并扣 `balance`；然后 `daily_bonus_left = 0`（`daily_bonus_day` 不动）。
   - 每次扣费之前先调用它——这样即使用户不登录、只是 DSH 在后台用 token，昨天的赠送也不会被今天花掉。
3. **发放**（`grantDailyBonus`，先执行 2）：`dailyBonusMicro > 0`、用户 `status = active`、`daily_bonus_day ≠ 今天` → 写 `daily` 流水（`+dailyBonusMicro`），`balance += 额度`，`daily_bonus_left = 额度`，`daily_bonus_day = 今天`。
   - 触发点：`POST /api/auth/login` 成功、`GET /api/auth/me`（打开 Hub 任何页面都会调）、`POST /api/me/instance/start`（含唤醒页）、`GET /api/me/compute`。一天只会成功一次（以 `daily_bonus_day` 判定，并发安全靠事务）。
   - 管理员账号同样发放（无害）；待审批 / 停用账号不发。
4. **对账不变量不变**：`balance = Σ ledger.amount − Σ usage.cost`（`daily`、`expire`、`compute` 都在 ledger 里）。新增测试钉住含赠送与算力的场景。
5. 显示：「今日赠送剩余」= `min(daily_bonus_left, max(balance, 0))`，用户端注明「今日有效，不累计」。

## 3. 计费规则（D3、D4）

以下只对**计费租约**（`billed = 1`）生效；免费租约只记录，不扣费、不宽限。

| 时刻 | 动作 |
| --- | --- |
| 开机前（准入） | `grantDailyBonus` → 余额 ≥ 1 块价格，否则 `402 INSUFFICIENT_POINTS`（`details: {balanceMicro, blockPriceMicro}`），不启动 |
| 实例进入 running | 同一事务：建租约 + 扣第一块（`compute` 流水，note `<规格名> 10 分钟`）+ `paid_until = 现在 + 10 分钟`。**续接**：同一用户最近一条已结束租约**规格相同**且 `paid_until > 现在` → 继承 `paid_until`，不扣（停了马上再开不重复收钱） |
| 每 30 秒结算（`tick`） | 对每条进行中的计费租约：`now ≥ paid_until` 时循环——`balance > 0` → 扣一块、`paid_until += 10 分钟`、清除宽限；`balance ≤ 0` → 若未在宽限则 `grace_until = now + graceMinutes`，跳出 |
| 宽限中充值 | 下一轮 `balance > 0` → 扣一块，`paid_until = now + 10 分钟`（**从现在起算**，宽限期免费），清除 `grace_until` |
| `now ≥ grace_until` | `instances.stop(userId, {reason:'insufficient'})`，租约结束 `insufficient`，审计 `instance.stop`（reason `insufficient`） |
| 停止（任何原因） | 结束租约：`ended_at`、`end_reason`；当前块不退款 |
| Hub 重启 | 容器不受 Hub 重启影响，照样在跑：先对账，再 `tick` 按 `paid_until` **补扣**停机期间的块（一轮内循环扣到 `paid_until > now` 或余额 ≤ 0） |

- 「余额」一律指钱包 `balance`；续费门槛是 `> 0`，所以最后一块可能把余额扣成小额负数（< 1 块），与 12 §6.4 的「略微为负」口径一致；下次充值先抵掉。
- 扣费前先 `expireStaleBonus`（§2.2）。
- `tick` 只改库，停机走 instances 的公开 `stop`（它自己拿用户锁）；`tick` 自身串行（上一轮没跑完不开新一轮）。
- 计费总开关从开到关：下一轮 `tick` 把所有进行中的计费租约以 `billing-off` 结束，实例**不停**。从关到开：已在跑、没有租约的实例继续免费跑到停止为止（管理端标「未计费」）。

## 4. 与实例生命周期的集成

instances 模块新增**晚绑定钩子**（compute 启动时注册，避免循环 import；未注册 = 现状）：

```ts
interface ComputeHooks {
  /** 实例当前应使用的 CPU/内存：有进行中租约 → 租约快照；计费开启 → 用户已选规格；否则 null（用 Quota） */
  currentSpec(userId: number): { cpus: number; memoryMb: number } | null
  /** 启动准入（在用户锁内、建容器前调用）：发每日赠送、解析并记住规格、查余额与内存容量；失败抛 HubError */
  beforeStart(userId: number, ctx: { reason: StartReason; planId?: string }): void
  /** 实例进入 running 后：没有进行中租约就开租（计费的扣第一块） */
  onRunning(userId: number, ctx: { reason: StartReason }): void
  /** 实例离开 running（stop / 对账发现退出或消失 / 启动失败）：结束进行中租约 */
  onStopped(userId: number, reason: ComputeLeaseEndReason): void
}
```

- `resolveQuota` 的结果在构造容器规格（`buildSpec`、`expectedHash`、`getStats` 的内存上限）时，用 `currentSpec` 覆盖 `cpus`、`memoryMb`；其余字段（pids、磁盘、空闲回收、插件权限）仍来自 Quota。规格不受 `QuotaSchema` 的 8 核 / 8 GB 上限约束。
- 钩子在用户锁内被调用，**不能再调 `withUserLock`/`stop`/`ensureRunning`**（会死锁）；compute 里需要停机的地方（`tick`）只在锁外调用 `instances.stop`。
- 各启动来源：

| 来源 | 租约 |
| --- | --- |
| 用户在工作台启动 / 唤醒页 / `login`（reason `user`、`login`） | 计费租约；本人是管理员且 `billAdmins = false` → 免费租约 |
| 管理员在后台启动别人的实例（reason `admin`） | **免费租约**（管理员决定的，不扣用户的钱）；规格用该用户已选规格 |
| restart / recreate / 下发任务（rollout）作用于**正在运行**的实例 | 沿用进行中租约，不新开、不重复扣 |
| rollout 启动了一个原本停止的实例 | 免费租约（同管理员代启动） |
| 换规格（§6 `PUT /api/me/compute/plan`，运行中） | 结束旧租约 `plan-change` → 按新规格 recreate → 新计费租约（扣第一块；规格不同不续接） |

- `StartReason` 增加 `'insufficient'`（只用于停止）。结束原因映射：stop 的 reason `user`→`user`、`admin`→`admin`、`idle`→`idle`、`insufficient`→`insufficient`、其它→`system`；对账判定 error、启动失败 → `crash`；对账发现容器消失 → `system`。
- **内存准入**（`capacityMemoryMb > 0` 时）：Σ（运行中/启动中实例的内存：有租约用租约，否则用 Quota，不含本人）+ 本次规格内存 ≤ `capacityMemoryMb`，否则 `503 CAPACITY_FULL`（`details: {committedMb, requestMb, capacityMb}`）。原有 `capacity.maxRunning` 检查保留。
- **空闲回收不变**（05 §6）：空闲停机即结束租约，用户不会为没人用的时间付费超过 `idleStopMinutes`。
- 唤醒页（`/dsh/<用户名>/` 实例没在跑时）仍调 `POST /api/me/instance/start` 不带请求体 → 用已选规格；`402` 时显示「积分不足」+ 跳工作台的链接（文案在 `WAKE_ERROR_TEXT`）。

## 8. 测试要点

- 纯函数：块价格向上取整；`tick` 状态机（正常续费、余额正好为 0、宽限开始/到期/中途充值、Hub 停机补扣多块、补扣中途余额耗尽）；每日赠送（同日重复触发只发一次、次日作废 + 重发、余额为负时的作废额、消费先用赠送）。用可注入时钟。

**WP17a 实现口径（2026-10-18，对上面未写死之处的取舍）**

- 计费总开关关闭时**不开任何租约**（包括免费租约），实例照旧按 `Quota` 运行；从关到开时已经在跑、没有租约的实例保持「未计费」直到停止（§3 已写，这里明确「关闭期间不补记免费租约」）。
- 管理员代启动 / `rollout` 启动原本停止的实例是免费租约，**启动准入不查用户余额**（`admin` / `rollout` 的 `beforeStart` 跳过余额检查）；内存准入仍然生效。
- `restart` / `recreate` 作用于已有进行中租约的实例时沿用旧租约：`beforeStart` **不做余额/内存准入**，也不要求该规格现在仍可选（管理员停用旧规格后仍能重建）；新租约仍只在没有进行中租约时开。
- `POST /api/me/instance/start` 带 `planId` 时**先校验并记住规格**（实例已在运行时也返回 `400` 而不是静默忽略），但已经在运行不会因此重启或换规格——换规格走 `PUT /api/me/compute/plan`。
- 宽限中充值在同一轮 `tick` 里优先于「宽限到期」判定：余额 > 0 时先扣一块、清除宽限，不会因为恰好到点而停机。
- 算力扣块只写 `relay_ledger`（`compute`，负数），**不改 `total_spent`**——后者保持「token 累计消耗」口径（§3 的扣费说明）。
