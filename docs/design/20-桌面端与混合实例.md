# 20 DSH Hub 桌面端 + 混合实例（需求整理 v0.1，2026-10-21）

> 实现状态更新于 2026-10-22：WP25–26 已交付，WP28/29/31 已合并；本轮发版验收记录未随开源版发布。以下需求段保留原始研究口径。

## 0. 用户原始诉求（2026-10-21）

1. Desktop login switches to our own (Hub) accounts, so a logged-in user carries a **role** and **points**.
2. After login, the admin console can push **plugins**, **configuration**, and even **upgrades** to the client.
3. Fix the Windows environment problems: **PowerShell, Python, proxy**.
4. The Claude Code / Codex bridge modes (dsh-claude-pilot / dsh-codex-pilot) also need to be integrated.
5. The client ships with a set of default plugins, and the admin console can push more.
6. Hub "instances" are split into two kinds: **Docker instances** (existing) and **desktop instances** (new). For desktop instances, **the Hub must not access the user's information**.

## 1. 基线事实

- The desktop upstream is `deepseek-ai/deepseek-harness` (MIT), `apps/desktop` (Electron shell) + `apps/desktop-host`. Read its source from a shallow clone of the upstream repo at the release tag you build against.
  - The Electron RunAsNode subprocess runs the shared profile runner, the window loads the bundled web client from `dsh-app://app/`, and the host listens on 127.0.0.1 on a random port. The `desktop` profile name is reserved for Electron.
  - It already bundles standalone **Python** (numpy/pandas/python-docx and more), **Node.js** and **pnpm** (`resources/runtime/primary-runtime`). That is a starting point for the Windows Python problem.
  - It already has an **auto-update** path (fixed Nightly feed with polling) and a **mandatory update policy** (`DSH_DESKTOP_MANDATORY_UPDATE_*_ORIGIN`, which requests `/api/v0/check_client_update`; error code 40005 is the forced-update modal). This could be pointed at the Hub.
  - The current login is a DeepSeek account (`packages/credentials/deepseek-account*`, `packages/client/ui-settings-account`).
  - Shell settings live in `%APPDATA%\@deepseek-ai\dsh-desktop\desktop\settings.json` (separate from the host config).
- On the Hub side we can reuse: user / role / invite code / points (wallet) / relay (per user × scope system key) / plugin library / `rollout.*` delivery jobs / `GET /v1/hub/agent-mode` (the pilots' Hub mode).
- The two pilots are currently verified only on Linux (Hub containers). In Hub mode they get their configuration from container env `HUB_*`.
- On a Windows dev machine, WSL interop can call Windows PowerShell 5.1, so real Windows checks are possible.

## 3. 需求拆解

### R1 登录与账户（诉求 1）
- R1.1 Unauthenticated desktop users first see a "Log in to Hub" screen. Proposed flow: the system browser opens the Hub's authorization page, the user logs in, and the client receives a token through a 127.0.0.1 loopback callback with PKCE. Fallback: device code. **[待确认: whether to allow typing the account and password directly in the client]**
- R1.2 The token is **per device** and can be revoked. Users can see and revoke their own devices in the Hub; admins can revoke any user's devices.
- R1.3 After login, the account row shows username, role, and points balance. Points come from the existing wallet, and models are billed through the relay.
- R1.4 The official DeepSeek account login is hidden or removed. **[待确认: whether to keep it as an "advanced" option]**
- R1.5 When the token expires or is revoked, the client returns to the login screen without losing local sessions.

### R2 下发：插件 / 配置 / 升级（诉求 2、5）
- R2.1 **Desired-state pull**: the client asks the Hub for its "desired state manifest" at startup and on a timer (plugins + versions + source, config fragments, minimum and target app versions, revision), applies it locally, and reports back what was applied and any errors.
- R2.2 Plugins come from the Hub plugin library as tgz files with hash verification, installed through the client's built-in plugin manager. Plugins are divided into **core** (users cannot uninstall), **default** (users can disable), and **optional**.
- R2.3 Config pushes may only write to a **whitelist of keys** (model providers / presets / pilot config / proxy, and similar). Pushing arbitrary commands is not allowed.
- R2.4 Upgrades: the Electron updater feed and the mandatory update policy both point to the Hub. Admins set the target version and minimum version per role or user, with staged rollout. The Hub hosts the installer and differential packages.
- R2.5 Admin console: in the existing 「下发」 delivery flow, add desktop targets, and show each device's apply status.
- R2.6 Default bundled plugins (draft): hub-connector (this document's login/delivery/reporting plugin, core), dsh-claude-pilot, dsh-codex-pilot, and dsh-memory. **[待确认: the list]**

### R3 Windows 环境（诉求 3）
- R3.1 PowerShell: **Decided (user, 10-21): bundle PowerShell 7 (portable build) and make it the agent's default.** Upstream `pwsh-local` already supports the `pwshPath` setting (`packages/shell/pwsh-local/src/resolve.ts`), so pointing that setting at the bundled copy needs no core code changes. The exact version is the current LTS, chosen in D4 (7.1 is end-of-life). D4 also compares 5.1 vs 7 on the user's Windows machine.
- R3.2 Python: by default, agents use the bundled Python. Decide how it coexists with the user's system Python and conda (PATH order, pip mirror pointing at a domestic mirror).
- R3.3 Proxy: **Revised 10-21 (D4 findings):** Hub traffic, model traffic and plugin downloads share one proxy policy, taken by default from the Windows system proxy (WinINET), and the Hub can push per-channel overrides. Forcing the Hub connection direct is wrong: the Hub is on the public internet, and Node in upstream ignores the system proxy. See desktop-plan/裁决.md #21.
- R3.4 Other: Git Bash or bash (needed by Claude Code on Windows), CRLF, Defender / SmartScreen (unsigned installers), code signing **[待确认: whether to buy a code-signing certificate]**.

### R4 Claude Code / Codex 桥接（诉求 4）
- R4.1 The two pilots run on desktop Windows: the claude / codex binaries get installed or bundled (npm or a standalone binary), with paths and child-process handling (Windows has no SIGTERM, so `.cmd` shims are involved).
- R4.2 Hub mode no longer relies on container env. The hub-connector provides `HUB_*` equivalent configuration to the pilots, using the device token in place of the container token. Billing stays under the `claude-code` / `codex` scope.
- R4.3 Login: on desktop, Hub mode is the default. Whether users can log in with their own subscription accounts is the same question as WP23 (we don't push subscription accounts). **[待确认]**

### R5 Hub 混合实例（诉求 6）
- R5.1 Instances gain a `kind: docker | desktop`. A desktop instance = one device record (device id, name, OS, app/runtime version, plugin list, last online, applied revision).
- R5.2 **Privacy boundary** (hard requirement): the Hub only receives the metadata in R5.1. It does not receive session content, workspace file names/contents, or local paths. Reporting fields go through an allowlist, and the client shows the user "what was reported". The Hub provides no remote-execution capability. Relay requests keep their existing behavior (usage metadata only). **[待确认: whether crash logs and diagnostics may be reported (only after user confirmation)]**
- R5.3 Admin instance list: Docker and desktop instances side by side. Desktop instances only allow "push / revoke device / view status".
- R5.4 Whether one user may have both kinds at once (default: yes), and the device limit **[待确认]**.

### R6 品牌与分发
- Product name, icon, and installer branding are the fork's own decisions. Distribution: download from the Hub web page, so the Hub must be reachable over HTTPS from the client — that reachability is the biggest external risk (it affects login, delivery, and updates).

## 5. 第一轮结论（2026-10-21 晚，D1–D6 全部验收）

The six research reports (D1–D6) and the cross-task rulings (#1–#22) belong to the fork's private planning material; where they conflict with the design docs, the design docs here win.

- **Build**: the fork keeps its own build script. It cross-builds an unsigned win-unpacked package (package size measured in the fork) and centralizes branding in one module. The official update, mandatory-update and telemetry endpoints are switched off. It starts on real Windows. A signed NSIS installer needs a Windows x64 build host with the MSVC toolchain and the Windows SDK.
- **Login**: upstream already does browser + loopback + PKCE. hub-connector implements the `DeepSeekAccount` abstract class and is swapped in by overriding one composition line. Device tokens are control-plane only. Each device gets its own relay key.
- **Devices**: a separate table `desktop_devices` (migrations 120–139). Reports go only to `POST /api/desktop/devices/report` (17-field allowlist, strictObject).
- **Delivery and upgrades**: `GET /api/desktop/manifest` (JSON Schema already exists) → PluginManager.installBundle + `cordis.hub.patch.yml` overlay. v1 upgrades use a single generic feed on the Hub + `/api/v0/check_client_update` for the global floor + manifest minVersion.
- **Windows**: bundle pwsh 7.6.7 and keep the encoding preamble. Put the bundled Python first in PATH and set PYTHONUTF8. Read the system proxy into Host env.
- **Bridge**: there are 6 Windows bugs in each of the two pilots (draft diffs exist). Add `POST /api/desktop/agent-mode-key`. **Do not redistribute Claude binaries** (neither in the installer nor hosted on the Hub).
