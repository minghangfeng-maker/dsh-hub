## 2. 非目标（本期不做）

| 不做 | 原因 / 替代 |
| --- | --- |
| 在线充值、对外收费 | （2026-10-16 修订）Hub 自带模型中转站后**有按量扣费**，但单位是内部「积分」（1 积分 = 1 元），只由管理员加/扣，不接支付，见 12 §0 |
| 邮箱验证、找回密码邮件 | 没有域名与发信策略；忘记密码由管理员重置（生成一次性临时密码，强制下次登录修改） |
| 多台宿主机/集群调度 | 只有一台 Hub 主机；`ContainerDriver` 抽象留好口子 |
| ~~管理员进入用户的 DSH~~ | （2026-10-18 修订）**改为允许**：管理员可从「实例」页打开任何未删除用户的 DSH（看得到对方的会话与文件）；每次进入写审计 `instance.admin.open`（同一对管理员/用户 10 分钟内合并为一条）。普通用户仍只能进自己的（02 §7） |
| 用户之间共享工作区/协作 | 每人一个完全独立的环境 |
| 手机 App | 前端做响应式；DSH 本身的移动端适配不在本项目范围 |

## 3. 已做的决策（可在评审时推翻）

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 后端 **Node 24 + TypeScript + Fastify 5 + SQLite（`node:sqlite`）** | 与 DSH 同栈（复用 cookie 签发/反代代码）；零原生依赖，免编译；单机几十人规模 SQLite 足够 |
| D2 | 前端 **Vue 3 + Naive UI + UnoCSS** | Naive UI 主题变量覆盖彻底（适合定制品牌风格），TS 友好；UnoCSS 做布局与动效原子类 |
| D3 | 容器运行时走 **Docker Engine API**（`dockerode`），可通过 `DOCKER_HOST` 切到 podman 的兼容套接字 | Docker 的生态与镜像最成熟，`dockerode` 也只用 Docker Engine 的常用子集；podman rootless 同样可用，开发期无需 sudo 也能跑集成测试 |
| D4 | 每个用户的 URL 标识用**不可变 slug**（`u` + 7 位小写字母数字，如 `u7k2m9x`），与用户名解耦 | 需求 2 允许改用户名；URL、容器名、目录名都不该随之变化，也不在 URL 里暴露用户名 |
| D5 | DSH 在容器内绑定**容器自己的 IP**，Hub 直连容器 IP，`Host` 改写为 `dshhub-<slug>:3000` 并以 `--trusted-host` 放行 | DSH 拒绝 `--host 0.0.0.0`；不发布任何宿主端口；每用户 authority 不同 → cookie 名天然不同 |
| D6 | 管理员下发的配置（模型、插件配置）写进**只读挂载的 `--patch` 覆盖层** `managed.patch.yml` | DSH 配置分层里 `--patch` 优先级最高，且 DSH 会拒绝被它覆盖的表单写入 → 管理员配置不会被用户改掉，用户自己的设置仍保存在自己的 profile 里 |
| D7 | 插件安装 = 修改用户 profile 的 `package.json`（依赖 + `dsh.profile.bundles`）后在容器里 `pnpm install`；本地插件由 Hub 打包成 `.tgz` 放进只读插件仓库 | 这就是 DSH 自己的插件模型（profile 目录里的 `package.json`，见 05 §1 F7）；`link:` 依赖在容器里不可用 |
| D8 | DSH 版本 = 运行时镜像 tag（`dshhub/runtime:<DSH 版本>`）；统一更新 = 构建新镜像 → 金丝雀 → 批量重建容器，失败自动回滚到旧镜像 | 数据都在卷上，重建容器无损；版本可按用户钉住 |
| D9 | 模型密钥以**容器环境变量**注入（`apiKeyEnv` 引用），密钥在 Hub 库里 AES-256-GCM 加密存放 | DSH 凭据解析里环境变量优先级最高且在界面只读；改密钥 = 重建容器（约 3 秒） |
| D10 | 导出格式默认 ZIP（Windows 双击可开），可选 tar.gz；永远排除 `.credentials.yaml`、`.env`、`node_modules`、缓存 | 用户要的是「资料」，不是可执行环境；凭据不出库 |
| D11 | 公网入口 L4 转发 + PROXY protocol，TLS 在 Hub 主机终止 | 满足需求 6，且能拿到真实客户端 IP 做限流与审计 |
| D12 | 开发阶段用 git worktree：每个任务包一个分支、一个 DSH 会话，编排者负责评审与合并 | 并行开发不互相踩文件 |
| D13 | **生产与开发都在同一台 Linux 主机上**（发行版不限，容器引擎就是这台机器上的 Docker Engine）；两者用数据目录/网段/端口/命名前缀隔开 | 单机够用、少一台机器要维护；剩余风险与 B 计划见 02 §3 |
| D14 | （作废）原计划专用发行版 + rootful podman，改为 B 计划，见 08 附录 A | — |
| D15 | 用户网段 `10.213.0.0/20`；出网规则用独立 nftables 表 | 避开 Docker 默认地址池；不依赖 `DOCKER-USER` 链 |
| D18 | **用域名**：`hub.<你的域名>`，A 记录指向公网入口；真实域名只写进部署方的 `hub.env`/`acme.env`，仓库里用 `hub.example.com` | 去掉「每台设备装根证书」这个最大门槛；仓库保持可开源 |
| D19 | **对外端口按需选择**：可以是标准 443，也可以是任意非标准端口（例如 `8443`），不要求独占 80/443 | 与机器上已有的站点并存即可（443 上按域名分流，或干脆换一个端口）；部分机房会按域名备案拦 80/443，非标准端口通常不拦（无官方保证）。所选端口要在浏览器受限端口名单之外；用户不写 `https://` 直接输 `域名:端口` 时，Hub 用同一端口 301 到 https |
| D20 | **证书 = Let's Encrypt，由 Hub 主机上的 acme.sh 用 DNS-01 签发**，Hub 热加载；不再做自签根 CA 与 `/ca.crt` | DNS-01 不需要对外开 80/443（这两个端口常被占用或被机房策略拦）；私钥只落在 Hub 主机，T9 不变 |
| D21 | **跨机入口 = 四层隧道**（frp、`ssh -R`、云厂商负载均衡或专线，任选其一） | 云端只给一个公网入口时，Hub 主机主动拨出即可，不要求入口机器能反向连 Hub；一条长连接承载全部流量，比按服务开一堆 `ssh -R` 好维护 |
| D22 | **四层转发示例用 HAProxy**（`mode tcp` + `send-proxy`），nginx 的 stream 模块也可以 | HAProxy 默认不监听任何端口、配置全显式；多数发行版的 nginx 包会自带一个抢 :80 的默认站点，得额外关掉 |
| D17 | **分两阶段交付**：阶段一「本地可用」——Hub 只监听本机 `http://127.0.0.1:7700`，全部功能在本机浏览器里跑通并验收；阶段二「公网入口」——再加 TLS、PROXY protocol、反向隧道与公网入口 L4 转发 | 先把产品本身做对，再处理入口 |

| # | 问题 | 结论 |
