## 1. 概念

| 术语 | 含义 | 表 |
| --- | --- | --- |
| 渠道 channel | 一个上游端点：`baseUrl` + 支持的协议 `apis` + 一组上游密钥（密钥池）+ **倍率**（千分比，默认 1000 = ×1.0）+ 优先级/权重/并发上限/超时/代理 | `relay_channels`、`relay_channel_keys` |
| 对外模型 model | 用户请求里写的 `model` 名、显示名、**价格**（输入 / 输出 / 缓存读 / 缓存写，积分/百万 token；每次请求，积分/次）、DSH 参数（上下文等）。价格与渠道无关；通过**路由**挂到一个或多个渠道（同名模型在第二个渠道里勾选 = 只加一条路由），路由可把名字改写成上游的叫法（高级用法） | `relay_models`、`relay_routes` |
| 钱包 wallet | 每用户一个：余额（微积分）、倍率、并发上限、每日上限、开关 | `relay_wallets` |
| 流水 ledger | 管理员加/扣积分、注册赠送（每次请求的扣费不进流水，记在用量里） | `relay_ledger` |
| 用户密钥 key | `sk-dsh-` + 40 位 base62。`system` = DSH 内置（每人一把，自动注入容器）；`user` = 用户自建 | `relay_keys` |
| 用量 usage | 每次转发一条：模型、渠道、token、费用、耗时、状态；另有按天汇总 | `relay_usage`、`relay_usage_daily` |
| hub-relay 提供方 | 模型提供方的新类型：把中转站当成一个 pi-ai 提供方渲染进用户 DSH（§7） | `model_providers.is_relay` |

外部工具 ──https://<域名>/v1（走对外入口）──────────┘   ① 认证 sk-dsh-… → 用户/钱包（余额>0、未停用、未超日限、并发未满）

## 3. 网络：容器怎么够到中转站

用户容器出网规则（02 §4）禁止连宿主。中转站在 hub-api 里，所以开一个**专用的内部监听器**，并在 nft 里只放行这一个口：

| 项 | 值 |
| --- | --- |
| 监听地址 | 用户网络 `HUB_USERS_NETWORK` 的网关 IP（生产 `10.213.0.1`，启动时向 Docker 查；`HUB_RELAY_INTERNAL_HOST` 可覆盖） |
| 端口 | `HUB_RELAY_INTERNAL_PORT`，默认 `7710`；`0` = 不开 |
| 内容 | **独立的 Fastify 实例**，只挂 `/v1/*` 与 `GET /healthz`；不读 cookie、没有 CSRF/会话、不托管静态文件；其它路径 404 |
| 绑定失败（网络还没建 / 地址不存在） | 记 warn，每 30 秒重试；概览页告警 `internal-listener-down` |
| nft 例外（02 §4 `chain in`，放在 `drop` 之前） | `ip saddr 10.213.0.0/20 ip daddr 10.213.0.1 tcp dport 7710 accept` |

同一套 `/v1/*` 路由**也挂在主应用上**（7700 本机、7443 公网），给外部工具用；主应用的会话/CSRF/Origin 钩子与 SPA 兜底必须跳过 `/v1/`。
公网入口还没开、或入口被机房按备案/域名策略拦截时（中国大陆机房常见），外部工具就只能先在主机本机或内网用；DSH 容器走内部监听器，不受影响。

`source` 字段：内部监听器 = `internal`，7700 = `local`，7443 = `public`。

## 4. 对外接口 `/v1`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/models` | 该用户可见的已启用模型。一份数据同时满足两家格式：`{ object:'list', data:[{ id, object:'model', type:'model', display_name, created, created_at, owned_by:'dsh-hub' }], has_more:false, first_id, last_id }` |
| POST | `/v1/chat/completions` | 协议 `openai-completions` |
| POST | `/v1/responses` | 协议 `openai-responses` |
| POST | `/v1/messages` | 协议 `anthropic-messages` |
| POST | `/v1/messages/count_tokens` | 透传给能走 `anthropic-messages` 的渠道，不计费、不记用量 |

**鉴权**：`Authorization: Bearer sk-dsh-…` 或 `x-api-key: sk-dsh-…`（两种都认）。按 `sha256(key)` 查 `relay_keys.key_hash`。
同一来源 IP 每分钟最多 20 次无效密钥，超过 429（复用 `lib/rate-limit.ts`）。内部监听器另有每 IP 每分钟 600 次的总量保护。

**请求体**：JSON 对象，`model` 必须是字符串；上限 32 MB（图片 base64）。

**错误**：按入口协议给对应格式——`/chat/completions`、`/responses`、`/models` 用 OpenAI 格式
`{ "error": { "message", "type", "code" } }`；`/messages*` 用 Anthropic 格式 `{ "type":"error", "error": { "type", "message" } }`。

| 情况 | HTTP | code（OpenAI）/ type（Anthropic） | 中文 message 示例 |
| --- | --- | --- | --- |
| 缺密钥 / 密钥无效 / 已停用 | 401 | `invalid_api_key` / `authentication_error` | 密钥无效 |
| 中转站总开关关闭 | 503 | `service_unavailable` / `api_error` | 中转站已关闭 |
| 用户钱包停用、账号停用/待审批/已删除 | 403 | `permission_denied` / `permission_error` | 你的模型使用权限已停用，请联系管理员 |
| 余额 ≤ 0 | 402 | `insufficient_points` / `permission_error` | 积分不足（余额 -0.12），请联系管理员充值 |
| 今日消耗已达上限 | 402 | `daily_limit_reached` / `permission_error` | 今日用量已达上限 |
| 用户并发已满 | 429 | `concurrency_limit` / `rate_limit_error` | 同时进行的请求过多 |
| 模型不存在 / 不可见 / 停用 | 404 | `model_not_found` / `not_found_error` | 模型 xxx 不存在 |
| 模型不支持该接口 | 400 | `unsupported_endpoint` / `invalid_request_error` | 模型 xxx 只能用 /v1/messages 调用 |
| 没有可用渠道（全停用/熔断/没密钥/渠道并发满） | 503 | `no_available_channel` / `overloaded_error` | 暂无可用上游 |
| 换遍候选仍失败（网络/5xx/429/401/403/超时） | 502（全是 429 时给 429） | `upstream_error` / `api_error` | 上游暂时不可用 |
| 上游 400/404/413/422 | 原样 | 原样（响应体透传） | — |

402 刻意不用 429：pi-ai 等客户端会对 429 自动重试，余额不足重试没有意义。

## 5. 转发

### 5.1 候选排序（`router.ts`，纯函数）

1. 取对外模型的**已启用**路由，过滤：渠道启用、渠道 `apis` 含本次接口的协议。没有 → 400 `unsupported_endpoint`（若存在启用路由但都不含该协议）或 503。
2. 每条路由的有效优先级/权重 = 路由上的值 ?? 渠道上的值。按优先级降序分层。
3. 同一层内用**加权会合哈希**（rendezvous hashing，键 = `userId + ':' + 模型名`）排序：同一用户同一模型稳定落到同一渠道（利于上游的提示缓存命中），整体又按权重分流。
4. 每个渠道内的密钥同样按 `userId` 会合哈希排序，跳过 `disabled`/`auto-disabled`/冷却中的。
5. 熔断中的渠道、并发已满的渠道排到最后（全都不可用时才用，仍不可用 → 503）。
6. 展开成「渠道 × 密钥」候选序列，最多尝试 `settings.maxAttempts` 个。

### 5.2 失败处理

只在**还没向客户端写出任何字节**时换候选：

| 上游结果 | 动作 |
| --- | --- |
| 连接失败 / 超时 / 5xx | 渠道 `fail_streak+1`，达到 `channelFailureThreshold` → 熔断 `channelCooldownSeconds`；换下一个 |
| 429 | 该密钥冷却 `max(Retry-After, keyCooldownSeconds)`；换下一个 |
| 401 / 403 | 该密钥 `auto-disabled`（记 `last_error`、审计 `relay.channel.key.auto-disable`、概览告警）；换下一个 |
| 400 / 404 / 413 / 422 | 不换，原样回给客户端（`client_error`，不计费） |
| 2xx | 渠道 `fail_streak=0`；开始流式回写 |

上游错误信息写进 `error` 前做脱敏（去掉形如 `sk-…`、`Bearer …` 的片段，截断到 300 字），永远不回显上游密钥。

### 5.3 请求改写

- 请求体：只改 `model` → 路由的 `upstreamModel`。`openai-completions` + `stream:true` + 渠道 `streamUsage` → 若没有就补 `stream_options.include_usage = true`。
- 请求头：**白名单**透传 `content-type`、`accept`、`user-agent`、`anthropic-version`、`anthropic-beta`、`openai-beta`；再叠渠道的 `headers`；
  鉴权按协议：`anthropic-messages` → `x-api-key: <上游密钥>`（没有 `anthropic-version` 时补 `2023-06-01`），其余 → `Authorization: Bearer <上游密钥>`。
  `cookie`、`x-forwarded-*`、客户端的鉴权头一律不转。
- URL：`{baseUrl}/chat/completions` | `/responses` | `/messages` | `/messages/count_tokens` | `/models`（`baseUrl` 去掉末尾 `/`）。
- 代理：渠道 `proxyUrl` 非空时用 `undici` 的 `ProxyAgent`（新增依赖 `undici`，纯 JS）。hub-api 进程本身**不读**环境里的代理变量。

### 5.4 响应与流式

- 响应头只回 `content-type`、`cache-control`，加 `x-dshhub-request-id`；流式加 `x-accel-buffering: no`。
- **字节原样透传**（不重新序列化），同时把字节喂给旁路解析器（`usage-parse.ts`）。
- 客户端断开 → 中止上游请求；用已经看到的 usage 计费，没看到则估算（§6.3），状态 `aborted`。
- 超时：收到响应头前 = 渠道 `timeoutMs`；流式中两块数据间隔超过 300 秒 → 中止（`upstream_error`）。
- 首字节耗时 `ttftMs` = 发出请求到上游第一块响应体；`durationMs` = 整个请求。

### 5.5 usage 解析（`usage-parse.ts`，纯函数，三协议 × 流式/非流式都要有单测）

| 协议 | 非流式 | 流式 | 换算成 `input / cacheRead / cacheWrite / output / reasoning` |
| --- | --- | --- | --- |
| openai-completions | `usage` | 最后一个带 `usage` 的 chunk | `prompt_tokens` 含缓存：`cacheRead = prompt_tokens_details.cached_tokens ?? prompt_cache_hit_tokens ?? 0`；`input = prompt_tokens − cacheRead`；`output = completion_tokens`；`reasoning = completion_tokens_details.reasoning_tokens` |
| openai-responses | `usage` | `response.completed` 事件的 `response.usage` | `input_tokens` 含缓存：`cacheRead = input_tokens_details.cached_tokens`；`input = input_tokens − cacheRead`；`output = output_tokens`；`reasoning = output_tokens_details.reasoning_tokens` |
| anthropic-messages | `usage` | `message_start.message.usage`（输入与缓存）+ 最后一个 `message_delta.usage`（输出；有的上游在这里也给输入，取非零的较大值） | `input = input_tokens`（不含缓存）；`cacheRead = cache_read_input_tokens`；`cacheWrite = cache_creation_input_tokens`；`output = output_tokens` |

`reasoning` 已包含在 `output` 里，只作展示，不单独计费。

## 6. 计费与积分

### 6.1 单位

所有金额是整数**微积分**（1 积分 = 1 元 = 1,000,000 微积分）；价格单位「微积分 / 百万 token」。界面按「积分 / 百万 token」录入与显示（最多 6 位小数）。

### 6.2 公式（`billing.ts`，纯函数）

```
raw  = input × p_in + cacheRead × (p_cacheRead ?? p_in) + cacheWrite × (p_cacheWrite ?? p_in) + output × p_out   // 单位：微积分 × 百万
base = raw + p_perRequest × 1_000_000                                                                             // 同单位（每次费用并入）
cost = ceil( base × channelRatePermille × walletRatePercent / (1_000_000 × 1000 × 100) )                          // 微积分，向上取整
```

即：**费用 = 模型价格算出的费用 × 渠道倍率**（× 钱包倍率；钱包倍率默认 100%，只有管理员给某个用户单独打折/加价时才不是 1）。

- 渠道倍率取**实际服务这次请求的渠道**（失败切换后的最后一个候选）的当前值，快照写进 `relay_usage.channel_rate_permille`；没走到渠道的请求为 `NULL`。
- 乘积可能超过 2^53（百万级 token × 高价 × 倍率），**用 BigInt 整数运算**后向上取整，不用浮点。
- `client_error` 与 `upstream_error` 不计费（cost = 0，但记一条用量）。任一倍率为 0 → 费用为 0（照常记 token）。
- 模型价格全为 0（新导入、还没定价）→ 按 0 计费，概览告警 `models-unpriced`。

### 6.3 估算

上游没回 usage（断流、上游不支持 `include_usage`）时按字数估算并标 `estimated=1`：
输入 = 请求里所有文本内容（不含图片/base64）的「中日韩字符数 + 其他字符数 / 4」，输出 = 已透传的文本增量按同一规则。
估算比例高的渠道在概览里告警 `usage-missing`（提示关掉该渠道的 `streamUsage` 或换上游）。

### 6.4 余额、上限与并发

- 进门检查：钱包启用 && `balance > 0` && （未设日上限 || 今日已消耗 < 日上限）&& 用户进行中请求 < 并发上限。
- 结束时扣费：同一个 `db.tx` 里 `INSERT relay_usage` + `UPDATE relay_wallets SET balance = balance − cost, total_spent = total_spent + cost, last_used_at` + upsert `relay_usage_daily`。
- 并发请求可能让余额小幅变负（最多是并发数个请求的费用）；之后的请求被 402 挡住。这是有意的取舍，不做预扣。
- **对账不变量**（测试钉住）：`balance = Σ ledger.amount − Σ usage.cost`（按用户）。
- 钱包懒创建：第一次需要写的时候（注册、首次请求、管理员改设置或加/扣积分）建行；GET 接口不写库，没有钱包的用户按默认值显示（余额 0、倍率 100、启用）。注册时若 `signupBonusMicro > 0`，同事务写一条 `signup` 流水。
- 进行中计数（用户、渠道）只在内存；Hub 重启清零。

### 6.5 日期分桶

「今天」「本月」与 `relay_usage_daily.day` 一律按 **Asia/Shanghai（UTC+8，固定偏移）** 自然日，不依赖服务器时区。

## 7. 与用户 DSH 的集成（自动配好模型）

### 7.0 WP12 起：下发到 DSH（系统托管）

管理员只做三件事：**勾选要下发的模型**（来自渠道里加好的对外模型）、**选一个默认模型**、**下发**。下面 1–5 条的提供方/预设机制仍然是渲染的实现方式，但全部由 Hub 自动维护，界面上不再出现。

| 项 | 规则 |
| --- | --- |
| 选中集合 | `relay_models.dsh_enabled`（迁移 082）。只有**已启用且有可用路由**的模型能被选中（`blockedReason` 给出原因）；被选中后又被停用/没了路由的，保留选中但不渲染，并在 `warnings` 里提示 |
| 默认模型 | `settings` 表键 `relay_dsh` = `{ "presetId": <系统预设 id>, "defaultModelId": <模型 id> \| null }`。默认模型被删除/停用/取消选中/没了路由 → 自动改成剩余可下发模型里 `sort, name` 排第一的；一个都没有 → null |
| 每个模型用哪个协议 | `deliverApi` = 该模型可用接口里按 `RELAY_DSH_API_PREFERENCE`（openai-completions > anthropic-messages > openai-responses）取的第一个；**一个模型只渲染在一个协议下** |

| 密钥 env（WP13） | 所有 hub-relay 提供方共用一个 env 名 `HUB_MK_HUB`（同一把用户 system 密钥）：`apiKeyEnv` 渲染成它，`containerEnv()` 只注入它。这样路由增减不改变容器 env、不触发重建（只重启）。升级后第一次下发会因 env 名变化重建一次容器 |

| 同步时机 | 一个纯函数算出「期望的系统提供方 + 预设内容」，`syncDshPreset()` 与库里比对，**有变化才写并 `revision + 1`**。调用点：`PUT /api/admin/relay/dsh`；对外模型的增删改、导入、启停、改名、`info`/`compat`/可见性/**默认思考档位**变化；路由变化；渠道启停或 `apis` 变化（凡是可能改变渲染结果的地方）。改价格、改倍率、改密钥不触发 |

旧的「提供方」「预设」管理接口（06 §4、04 §4.7）保留不删（下发向导与测试仍在用），但**管理端界面不再提供入口**；之前手动建的提供方/预设不再被默认使用。

1. **提供方新类型 `hub-relay`**（契约 `ModelProviderKindSchema` 已加）。库里存 `kind='pi-ai'` + `is_relay=1`（迁移 044；改 CHECK 约束要重建表，风险大，所以加列），repo 层映射成 `hub-relay`。
   管理员只填路由名（建议 `hub`）、显示名（如「Hub 中转站」）、协议 `api`（三选一），可选 `compat`/`extra`；`baseUrl`、`models`、`keyMode`、`apiKey` 由 Hub 决定（请求里给了也忽略，返回值里 `baseUrl` = 内部地址、`models` = 实际会渲染的模型、`keyMode='per-user'`、`apiKey.set=true`）。
2. **渲染**（`models/render.ts`）：`baseURL = relay.internalBaseUrl()`（如 `http://10.213.0.1:7710/v1`）；`models` = 已启用、对该用户可见、`apis` 含该提供方协议的对外模型，字段取模型的 `info`（上下文、最大输出、输入类型、思考档位，规则同 06 §4.1）；
   `compat`：模型自己的 `compat` 写在模型条目上——**WP10a 先用真容器验证 llm-pi-ai 是否接受模型级 `compat`**（`docker run` 测试前缀容器、看有无 ValidationError），不接受就只用提供方级 `compat` 并在渲染警告里提示；
   内部监听器关闭 → 不渲染该提供方并给警告。一个用户可以有多个 hub-relay 提供方（如 `hub` 走 openai-completions、`hub-claude` 走 anthropic-messages）。
3. **密钥**：`containerEnv()` 对 hub-relay 提供方注入 `HUB_MK_<ROUTE>` = 该用户的 system 密钥（没有就当场签发并加密存 `key_enc`）。多个 hub-relay 提供方注入同一把。重置 system 密钥 → env 变 → `config_hash` 变 → 实例提示需要重建。
4. **何时需要重新下发**：对外模型的增删、启停、改名、`info`/`compat`/可见性变化，或渠道变化导致某模型的 `apis` 变化 → 把**所有包含 hub-relay 提供方的预设** `revision + 1`（复用现有「有 N 项待应用」与下发向导）；
   改价格、改密钥、改渠道优先级不影响渲染，不 bump。
5. 管理员最省事的用法：模型 → 提供方 → 新建「Hub 中转站」→ 加进默认预设并设默认模型 → 下发。中转站「模型」页在有待下发时给横幅，链接 `/admin/rollouts/new?kind=models`。

## 11. 安全与隐私

- 不存、不打日志：请求/响应内容、用户密钥明文（只存 sha256；system 密钥另存加密副本以便注入容器）、上游密钥明文（只存加密 + 末 4 位）。
- 内部监听器只有 `/v1`，独立 Fastify 实例，没有任何管理接口；nft 只放行网关 IP 的这一个端口，宿主其它端口、局域网规则不变（安全闸门 A 段照常通过）。
- 用户的 agent 能从 env 读到自己的 system 密钥（与原来的 per-user 密钥一样），能拿去别处用，但花的是自己的积分；管理员可停钱包。
- 资源保护：请求体 32 MB 上限；每用户并发上限；渠道并发上限；无效密钥按 IP 限流；内部监听器每 IP 总量限流。
- 上游的错误信息脱敏后才写库/回显。

## 13. 上线步骤（编排者 + 用户）

1. 合并 WP10a/WP10b → 备份数据库（带迁移 044/080）→ `fetch . main:release` → `deploy/upgrade.sh`。

3. `ss -ltnp | grep 7710` 确认监听在 `10.213.0.1:7710`；一次性测试容器（`--network dshhub-users`，名字 `dshhub-test-relay-*`）`curl http://10.213.0.1:7710/healthz` 通、`curl http://10.213.0.1:7700` 不通。
