# 16 模型按渠道拆成独立模型（下发、计费、显示）+ 工作台插件 / 数据区块重设计

> 2026-10-18 立项（用户提出，任务包 WP20）。
> **同日修订**：第一版的做法是「同一模型 id，按渠道分到不同的提供方」，派发后用户否决了，原话是「给用户明确的不同的模型选择，有多个就多个，而不是放到一起」。
> 现在改为：**每个「模型 × 渠道」组合就是一个独立的模型**，名字是 `<模型>@<渠道标识>`。下文都按修订后的方案写。

## 0. 问题与决策

**问题 1（UI）**：WP19 上线后，工作台的「我的插件」「我的数据」是从个人中心原样搬过来的，没有套卡片，和上面「我的 DSH」「我的模型」的风格不统一。插件网格最后一行常常只剩一张卡，数据区左边是表单、右边是历史，一高一矮，看起来「只有一部分」。

**问题 2（渠道打架）**：同一个对外模型挂在多条倍率不同的渠道上（例如 `deepseek-v4.1-flash` 同时挂在 `upstream-c 池` ×0.3 和 `upstream-b` ×0.1）。路由自动选渠道，带来几个问题：用户看到的价格是一个区间，不知道会按哪个价扣费；同一个用户每次扣费可能不一样，说不清楚；用户也没法自己选渠道。

| # | 决策 |
| --- | --- |
| D1 | 每条渠道有一个**对用户可见的标识** `slug`（如 `upstream-c`、`upstream-b`）。渠道的名称、地址、成本仍然不对用户公开 |
| D2 | **每个「模型 × 渠道」是一个独立的模型**，名字是 `<模型>@<slug>`，例如 `deepseek-v4.1-flash@upstream-c` 和 `deepseek-v4.1-flash@upstream-b`。一个模型挂了几条渠道，用户就看到几个模型。每个模型的价格是确定的，不再是区间 |
| D3 | 用 `<模型>@<slug>` 调用时**只走这一条渠道**，失败了也只在这条渠道的密钥之间切换，不会换到别的渠道（避免按更贵的价格扣费） |
| D4 | 下发到 DSH 时，DSH 的模型列表里每个组合都是一个独立的模型：模型 id 为 `<模型>@<slug>`，显示名为 `<显示名> · <slug>`（如「DeepSeek V4.1 Flash · upstream-b」）。提供方结构不变，仍然叫「DSH Hub」 |
| D5 | 用户端所有列模型的地方（工作台「我的模型」、积分与用量「可用模型」、`/v1/models`）**只列 `@` 形式的独立模型，一行一个，不按原模型分组**，每行显示「渠道 ×倍率」和确切价格。使用记录加「渠道」列 |
| D6 | 兼容：不带 `@` 的老模型名照常能调用（自动选渠道，按实际走的渠道计费），已有的外部工具和 API 密钥不受影响，只是界面和 `/v1/models` 里不再列出 |
| D7 | 计费公式不变（12 §6.2）：费用 = 模型价格 × 实际渠道倍率 × 钱包倍率 |

## 1. 现状（编排者 2026-10-18 只读查询生产库）

- 渠道：`upstream-c 池`（id 1，×0.3，**已停用**）和 `upstream-b`（id 2，×0.1，启用），都只支持 `openai-completions`，优先级 0，权重 1。
- 模型：只有一个 `deepseek-v4.1-flash`，在两条渠道上各有一条启用的路由，已选中下发到 DSH。
- 上线后：用户的 DSH 里只能看到 `deepseek-v4.1-flash@upstream-b`，因为 `upstream-c 池` 是停用状态。管理员重新启用 upstream-c 并勾选下发以后，才会多出 `@upstream-c`。

## 2. 渠道标识

- 字段 `relay_channels.slug`：小写字母、数字和 `-`，必须以字母或数字开头，最长 24 位，全局唯一（契约里的 `RELAY_CHANNEL_SLUG_REGEX`）。
- 新建渠道时可以不填，按名称自动生成：转成小写，只保留 `a-z0-9`，其他字符连成的段替换成 `-`，去掉首尾的 `-`，最多截到 24 位。结果为空时用 `ch<id>`；与已有标识冲突时依次加 `-2`、`-3`……管理员手动填写的标识如果冲突，返回 `VALIDATION_FAILED`（fields.slug）。
- 标识可以修改。修改会改变用户看到的模型名，所以要触发 `syncDshPreset`（需要重新下发）。编辑抽屉里给出提示：「改了以后，用户 DSH 里的模型名会变，要重新下发；外部工具里写的 `模型@旧标识` 会失效。」
- 迁移 **086**（relay 段）：`ALTER TABLE relay_channels ADD COLUMN slug TEXT`，并建唯一索引（`WHERE slug IS NOT NULL`）。已有渠道的空 slug 在 API 启动时按上面的生成规则补齐，记审计 `relay.channel.slug-backfill`。例如「upstream-c 池」会得到 `upstream-c`。

## 3. 按 `@` 调用（转发）

- 请求体里的 `model` 写成 `<模型>@<slug>`，适用于 `/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/messages/count_tokens`。解析顺序：先把整串当作模型名精确查找，找到了就按不指定渠道处理（兼容本来名字就带 `@` 的模型）；找不到时，按**最后一个** `@` 切开，后半部分必须是已存在的渠道标识，前半部分必须是已存在的模型。
- 候选只有这个模型在这条渠道上的那一条路由，以及这条渠道的密钥。**不会切到别的渠道。** 失败时：
  - 模型不存在，或在这条渠道上没有路由：404 `model_not_found`，提示「模型 X 不存在」（错误信息里写用户传的完整名字）；
  - 路由停用或渠道停用：503 `no_available_channel`；
  - 这条渠道不支持本次协议：400 `unsupported_endpoint`。
  - 渠道熔断中照样尝试，因为它是唯一的候选（同 12 §5.1 第 5 条）。
- 发给上游的请求体里，`model` 照常改写成路由的 `upstreamModel`，后缀不会带给上游。
- 会合哈希的键（12 §5.1 第 3 条）用模型本名，保证同一用户的密钥选择和以前一致。
- 用量：`relay_usage.model` 记录**用户请求的原始名字**（带 `@` 的就是带 `@` 的），用户在使用记录里看到的就是自己选的那个模型。另加两列（迁移 086）：`base_model TEXT`（模型本名，供按模型统计和对账用）和 `pinned INTEGER NOT NULL DEFAULT 0`。按模型统计（`byModel`）**按原始名字分组**，这样用户能分别看到 `@upstream-c` 和 `@upstream-b` 各花了多少。管理端用量记录可以按本名筛选。
- `/v1/models`：列出该用户可见的「模型 × 启用渠道上的启用路由」，`id = <模型>@<slug>`，`display_name = <显示名> · <slug>`；**不再列出**不带 `@` 的名字（它们仍然可以调用）。

## 4. 用户端

### 4.1 接口
- `/api/me/relay` 的 `models[].routes[]`（契约 `MyRelayModelRouteSchema`）：只包含启用渠道上的启用路由。字段有 `channelSlug`、`ratePermille`、`pinnedModel`、`inDsh`、`dshDefault`。模型级的 `inDsh` 等于「任一路由 inDsh」，`dshDefault` 等于「默认路由属于这个模型」。接口按模型嵌套返回；**前端负责展开成平铺的独立模型**（§4.2）。
- 用户的使用记录接口返回 `channelSlug`（公开信息）和 `pinned`；`channelId`、`channelName` 在用户端仍然返回 null。

### 4.2 工作台「我的模型」
- 把 `models[].routes[]` 展开成**平铺列表，每个独立模型一行**，不分组、不缩进。统一管理的用户只列 `inDsh === true` 的。排序：默认模型排第一，其余按倍率从低到高、再按名字排。
- 每行显示：模型名 `deepseek-v4.1-flash@upstream-b`（等宽字体，可复制），下面一行是显示名；渠道标签「upstream-b ×0.1」（倍率不等于 1 时用强调色）；确切的输入 / 输出 / 缓存读价格（积分 / 百万 token）；上下文长度；默认模型带「默认」标签。
- 手机宽度下每个模型一张小卡片。
- 钱包倍率不等于 100% 时的提示保留。
- 后端没有给 `routes` 时，退回 WP19 的显示方式。

### 4.3 积分与用量
- 「可用模型」：同样平铺成独立模型，列为模型（`@` 名，可复制）、渠道「slug ×倍率」、可用接口、确切价格、上下文。表头的 InfoTip 写：「模型名后面的 @ 表示走哪条渠道，价格按这条渠道算。」
- 「按模型」统计和「使用记录」里的模型列，直接显示请求时用的名字。使用记录另加一列「渠道」（「slug ×倍率」）；没走到渠道的显示「—」。

## 5. 管理端

- **渠道**：表格加「标识」列（等宽字体）。新建和编辑抽屉加「标识」字段，留空就自动生成；字段旁边用 InfoTip 说明「用户会看到它，模型名后面的 @ 就是它」。修改时的提示见 §2。
- **模型与价格**：模型行里的渠道胶囊改成显示「标识 ×倍率」，例如「upstream-b ×0.1」。
- **用量记录**：模型列显示原始名字，加一个按本名筛选的选项。

## 6. 下发到 DSH 按「模型 × 渠道」

### 6.1 存储与接口
- 迁移 086：`ALTER TABLE relay_routes ADD COLUMN dsh_enabled INTEGER NOT NULL DEFAULT 0`。回填规则：所属模型 `dsh_enabled = 1` 的启用路由都设成 1。`relay_models.dsh_enabled` 保留，由 Hub 维护成「任一路由被选中」。
- `settings.relay_dsh` 加字段 `defaultRouteId`。回填规则：在默认模型的可下发路由里，按渠道优先级从高到低、倍率从低到高、渠道 id 从小到大排序，取第一条。默认路由失效时，自动改成剩余可下发路由里排第一的那条（模型按 `sort, name` 排，同一模型内按上面的规则排）。
- `GET /api/admin/relay/dsh` 的每个模型带 `routes[]`（契约 `RelayDshRouteSchema`），响应顶层带 `defaultRouteId`。
- `PUT` 按契约两种写法二选一：新写法是 `routeIds` + `defaultRouteId`；老写法 `modelIds` + `defaultModelId` 等于选中这些模型的全部路由，默认路由按回填规则取。新勾上的路由如果不能下发，返回 `VALIDATION_FAILED`，details 里列出「模型@标识」和原因。原本已选中、后来才变得不能下发的路由照常接受。
- 路由级的 `blockedReason` 有四种：模型已停用、渠道已停用、路由已停用、模型和渠道没有共同支持的协议。

### 6.2 渲染
- 提供方结构**不变**，仍然按「协议 × 默认思考档位」分（WP13 的路由 id `hub`、`hub-anthropic`、`hub-max` 等，显示名都是「DSH Hub」），baseURL 也不变。
- 提供方下的模型从「每个模型一条」改为「**每条被选中且可下发的路由一条**」：
  - `id = <模型>@<slug>`
  - `name = <显示名> · <slug>`
  - 上下文等参数取自模型的 `info`（同一模型的各条渠道相同）
  - `deliverApi` 改为按路由算：模型的可用接口和渠道的 apis 取交集，再按 `RELAY_DSH_API_PREFERENCE` 取第一个
  - 默认思考档位取自模型
- 默认模型：`default_model = <模型>@<slug>`（默认路由），`default_provider` 是这条路由所在的提供方。
- 触发同步的时机：在 12 §7.0 列出的基础上，加上**渠道标识修改**和**路由选中状态变化**。改倍率仍然**不**触发。
- 密钥 env 不变（`HUB_MK_HUB`），所以从 WP19 升级上来时，用户容器只需要重启，不需要重建。
- 已有对话的影响：用户已有对话里选中的是 `deepseek-v4.1-flash`，下发后这个 id 不存在了，用户需要重新选一次模型（DSH 会回落到默认模型）。上线说明里要写上这一点。
- **真容器验证（WP20a 必做，结论写进报告）**：用测试前缀起一个容器，渲染两个模型 `m@a` 和 `m@b`（同一个本名），验证三件事：
  1. DSH 正常启动，没有 ValidationError，模型列表里两个模型分开显示，显示名正确；
  2. 分别选这两个模型对话，假上游 a、b 各自收到请求，请求体里的 model 是 upstreamModel，没有 `@`；
  3. Hub 的用量里记录的是 `m@a` / `m@b`，并按各自渠道的倍率计费。

  如果 DSH 不接受 id 里带 `@`，换用 `~` 作为分隔符（契约常量 `RELAY_PINNED_MODEL_SEPARATOR` 改一处即可），并在报告里说明。

### 6.3 管理端「下发到 DSH」页
- 列表平铺：**每个「模型@标识」一行**，和用户看到的一致。列为：复选框、模型名（`@` 形式）、渠道名 + 倍率、协议、默认思考、不能下发的原因、「设为默认」单选。可以按模型本名筛选。
- 页头显示「默认：deepseek-v4.1-flash@upstream-b」。
- 保存时发送 `routeIds` + `defaultRouteId`。后端没给 `routes` 时退回按模型选择的老界面，保存发老写法。

## 7. 工作台「我的插件」「我的数据」重设计（问题 1）

总原则：两块都放进和「我的 DSH」「我的模型」**一样的 `SoftCard`**，标题在卡片头部，操作放在头部右侧，内容占满卡片宽度。不能出现孤零零一张卡片占一行，或者左右两栏一高一矮的情况。

**我的插件**
- 卡片头部：标题「我的插件」，旁边小字「已安装 3 / 4」；右侧是分段筛选「全部 · 已安装 · 可安装」。筛选结果记在 localStorage 里，读写都要 try/catch。
- 内容是**紧凑列表**：桌面宽度两列等宽，手机一列。每行高度固定（约 64px），依次是：图标（36px）、名称（必装的带锁）、一行描述（超长省略，完整内容放 title）、版本号（等宽小字），最右边是状态标签和开关（必装插件只显示「必装」标签，没有开关）。同步中显示转圈；失败显示红标签，点开能看到原因。
- 筛选后没有内容时，用一句空状态文字，不要留大块空白。
- 轮询逻辑沿用 `MyPluginsTab`：每 3 秒一次，直到状态稳定。

**我的数据**
- 卡片头部：标题「我的数据」；右侧显示「上次导出：2026-10-18 16:13 · 1.2 GB · 下载」，从没导出过就不显示。
- 内容从上到下：
  1. 「打包内容」：四个**横排的可勾选块**（工作区 / 会话记录 / DSH 设置 / 插件清单），每块显示名称、大小和文件数。桌面一行四个，手机两列。
  2. 一行操作：格式选择（ZIP（推荐）/ tar.gz）、预计大小，右侧是「开始打包」按钮。
  3. 打包进行中时，在操作行下面显示进度：复用 `ExportProgressCard` 的逻辑，样式改成嵌在卡片里的进度条。
  4. 「历史导出」：紧凑表格，列为时间、包含内容、大小、状态、剩余有效期、操作。默认显示最近 3 条，点「查看全部」展开。
- 手机宽度单列，按钮占满整行。
