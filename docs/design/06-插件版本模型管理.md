# 06 插件 / DSH 版本 / 模型管理

管理员的三类「批量改用户环境」操作共用一套**下发任务（rollout）引擎**：先算出每个目标用户的
「期望状态」，再由任务引擎逐个用户执行「改文件 → 安装 → 重启 → 健康检查 → 失败回滚」。

## 1. 统一概念：期望状态 → 对账

| 对象 | 期望状态存放 | 实际状态 | 对账动作 |
| --- | --- | --- | --- |
| 插件 | `user_plugins.desired / desired_version_id` | `actual_version_id` + profile `package.json` | 改依赖与 bundles → `pnpm install` |
| DSH 版本 | `users.runtime_id`（空 = 默认版本） | `instances.runtime_id` | 用新镜像重建容器 |
| 模型配置 | `users.model_preset_id` + 提供方/密钥 | `managed/manifest.json` 的 `presetRevision` 与 `instances.config_hash` | 重渲染 `managed.patch.yml`；密钥变化则重建容器，否则只重启 |

任何时候实例 `start` 都会先做一次**轻量对账**（只比较哈希与 manifest，不装包）；
需要装包的差异标记为 `pending`，在状态页提示「有 N 项待应用」，由下发任务或用户点「立即应用」处理。

## 2. 插件目录

### 2.1 插件来源

| 类型 | 例子（取自你现在的 profile） | 入库方式 | 写进 `package.json` 的 spec |
| --- | --- | --- | --- |
| `npm` | `dsh-email@^0.16.0`、`@xmanrui/dsh-im@^4.35.1`、`@gausszhou/dsh-opencode-session-id` | 输入包名 → 从 npmmirror 拉元数据 → 选版本 | 精确版本 `0.16.0`（**不用 ^**，保证所有人一致） |
| `tarball` | `@demo-alice/dsh-remotion-video-plugin`（GitHub codeload tar.gz） | 填 URL + 版本标签 | URL 原样 |
| `local` | 宿主机上的插件目录（包名一般是 `@local/*`） | 填宿主目录 → Hub 执行 `pnpm pack`（在临时目录，不改原目录）→ 存入 `plugin-store/` | `file:/opt/hub/plugin-store/<文件>.tgz` |
| `upload` | 管理员上传 `.tgz` | 校验是合法 npm 包（含 `package.json`，`name` 与插件一致）→ 存入 `plugin-store/` | 同上 |

> ⚠ 你的 `@local/dsh-image-gen` 等插件的 `cordis.patch.yml` 里**可能含有令牌**（例如魔搭令牌）。
> 打包本地插件时，Hub 会扫描包内文件，发现疑似密钥（`sk-`、`ms-`、`token:`、`apiKey:` 等模式）就**拒绝入库**并提示改为
> 「插件配置 + 模型/密钥下发」的方式。需要密钥的插件，请把密钥放进插件的 `configYaml` 用 env 引用。

### 2.2 插件策略 `policy`

| policy | 含义 | 新用户 | 用户能否自己卸载 |
| --- | --- | --- | --- |
| `required` | 必装 | 首次启动自动装 | 不能（即使在 DSH 自己的插件管理里删掉，下次对账也会装回来） |
| `default` | 默认装 | 首次启动自动装 | 能 |
| `optional` | 可选 | 不装；在「我的插件」里可自助安装（配额允许时） | 能 |
| `hidden` | 下线 | 不装；不在列表展示 | — |

### 2.3 Hub 管理的边界

- Hub 只管理**目录里登记过**的插件。用户在 DSH 自带插件管理器里装的其它插件，Hub 不碰。
- 为了区分，Hub 在用户 profile `package.json` 里维护一个字段：

  ```jsonc
  "dshHub": { "managed": { "dsh-email": "0.16.0", "@local/dsh-file-download": "1.0.0" }, "updatedAt": "…" }
  ```
- 渲染 bundles 列表时保持顺序：**出厂 bundles（原样保留）→ Hub 管理的 bundles（按 `bundle_order`）→ 用户自装的 bundles（原样保留相对顺序）**。

### 2.4 单用户安装执行器（`plugins/installer.ts`）

```
installForUser(user, changes: { add: PluginVersion[], remove: Plugin[] }, opts: { restart: 'now'|'next-start' })
  withUserLock(user):
    1. 读 users/<slug>/home/.dsh/profiles/web/package.json（不存在 → 先确保 profile 已创建：S3）
    2. 备份为 package.json.hub-bak-<时间>（保留最近 3 份）
    3. 执行安装/卸载（WP0b S4：官方命令会同时写 dependencies（精确版本）与 dsh.profile.bundles）：
         安装 → dsh plugin --profile web add <spec>        卸载 → dsh plugin --profile web remove <name>（WP3 实测确认）
         实例 running → driver.exec(容器, 上述命令)；实例未运行 → driver.runOnce(同规格一次性容器, 同命令)
       环境：npm_config_registry=npmmirror；超时 10 分钟；输出实时追加到 task 日志
    4. Hub 再改写 package.json：按 §2.3 规则重排 dsh.profile.bundles（官方命令把新 bundle 追加在末尾），更新 dshHub.managed
    5. 失败 → 还原 package.json → 再跑一次 pnpm install（回到原状）→ 抛错
    6. 重渲染 managed.patch.yml（插件的 configYaml 可能变化）
    7. restart='now' 且实例 running 且（任一插件 needs_restart）→ 重启 DSH → 就绪检查（05 §6 判据）
       就绪失败 → 还原 + 重装 + 再重启 → 标记失败
    8. 更新 user_plugins.actual_version_id / state
```

> 已按 WP0b S4 结论定稿：安装动作走 `dsh plugin add`（实测 npm 包 8–13 s、本地 tgz ~1 s），顺序与回滚由 Hub 负责。

### 2.5 新用户 bootstrap

首次 `start` 时（`instances.bootstrapped_at` 为空），**在启动 DSH 之前**：实例服务调用
`plugins.bootstrapUser(userId)`，它用 `driver.runOnce`（同规格一次性容器，DSH 未运行）对所有 `required` + `default`
插件执行安装（`dsh plugin --profile web add …`，profile 不存在时由该命令自动创建），完成后写 `bootstrapped_at`，
然后再正常启动 DSH——一次启动就带齐插件，不需要「先起、装完再重启」。唤醒页显示阶段 `bootstrapping` 与进度（「正在为你准备插件 2/5…」）。
bootstrap 失败不阻塞启动：记 `user_plugins.state=failed`，DSH 照常启动，状态页提示「有插件没装上，可稍后重试」。

## 3. DSH 版本管理（运行时镜像）

| 操作 | 实现 |
| --- | --- |
| 查询可用版本 | `GET https://registry.npmmirror.com/@deepseek-ai%2Fdsh` → `versions` 与 `dist-tags`（缓存 10 分钟） |
| 构建 | `runtime.build` 任务：打包 `runtime/` 为 tar → `driver.buildImage(ctx, 'dshhub/runtime:<ver>', {DSH_VERSION, NPM_REGISTRY})` → 冒烟测试：`runOnce` 执行 `dsh --version` 必须等于目标版本 → `status=ready` |
| 设为默认 | `runtimes.is_default` 唯一；影响「未钉版本」的用户**下次重建**时使用的镜像；不会自动重建正在运行的容器 |
| 统一更新 | 下发任务 `kind:'runtime'`：对目标用户逐个 `recreate`（新镜像）→ profile `pnpm install`（依赖可能有原生模块）→ 就绪检查；失败 → 用旧镜像 recreate 回滚 |
| 钉版本 | 管理员在用户详情里设 `runtime_id`；钉住的用户不受「设为默认」影响，但仍可被显式下发 |
| 下线/删除 | `retired`：不能再被选为目标；删除：无用户使用 + 非默认 → `removeImage` |
| 初始化 | Hub 首次启动若没有任何 runtime，管理后台概览页提示「先构建一个 DSH 版本」，并预填本机版本 `0.2.0-rc.2` |

## 4. 模型配置

> **2026-10-16（WP12）**：用户 DSH 里的模型只来自 Hub 中转站。管理员在「模型 → 下发到 DSH」里勾选模型、选默认模型、下发；
> 下面的提供方 / 预设机制仍是渲染的实现方式，但由 Hub 自动维护一个系统预设「Hub 中转站」和 `hub*` 系统提供方（见 **12 §7.0**），管理端界面不再提供入口。

### 4.1 提供方（provider）

两种 `kind`：

- `pi-ai`：渲染进 `llm-pi-ai` 条目的 `providers.<routeKey>`。字段一一对应 pi-ai 的配置（`displayName`、`api`、`baseURL`、`models`、`compat` + `extra_json` 透传），
  `apiKeyEnv` 自动设为 `HUB_MK_<ROUTEKEY>`。
- `deepseek-official`：DSH 内置的 DeepSeek 直连路由，只需要密钥（env `DEEPSEEK_API_KEY`）。

`key_mode`：`shared`（全体共用一把，界面红字提示「用户 agent 能读取到该密钥」）、`per-user`（每个用户单独填，推荐，例如为每人在中转站签发一把下游密钥）、`none`（无需密钥的内网端点）。

「测试连接」与「从端点发现模型」：`openai-*` 用 `GET {baseURL}/models`（Bearer），`anthropic-messages` 用 `GET /v1/models?limit=1000`（`x-api-key` + `anthropic-version`），
与 pi-ai 的发现逻辑一致（见 `dsh-llm-pi-ai/README.md`「Discover models from endpoints」）。

模型条目除 `id`、`name` 外可填：`contextWindow`（上下文）、`maxTokens`（最大输出）、`input`（`text` / `image`，不填 = pi-ai 默认纯文字）、
`reasoningEfforts`（思考档位，见 `render.ts`：`off` 渲染成 `null`，只有 `off` 的声明会被丢弃并告警）。

**模型信息库**（`models/catalog.ts`）：按模型名自动补全上面这四项，免得每个模型都手填。
- 两层：内置（代码里的 `catalog-data.ts`，由 `scripts/gen-model-catalog.mjs` 从 pi-ai 自带目录生成，即 DSH 自己认的那份数据，升级运行时后重新生成）+ 自定义（`model_catalog` 表，管理端「模型 → 模型信息库」维护）。自定义同名字段优先，没写的字段用内置补。
- 匹配只做**精确的规范化匹配**，不做前缀 / 模糊匹配（宁可没匹配上让人手填，也不把别的模型的参数填上去）：忽略大小写、去厂商路径前缀（`a/b/c` → `c`）、去 `:free` 之类后缀、去日期后缀与 `-latest`、`. _` 统一成 `-`；同时对照条目的 `id` 与显示名（`id` 命中优先）。
- 「从端点发现」时服务端补全，参数优先级：端点列表自己报的（`context_length` 等，字段名同 pi-ai 的发现解析）> 自定义 > 内置；结果带 `infoSource` / `matchedId`，界面标明来源。
- 手填的模型：id 填完离开输入框自动补全空字段；「按模型库补全」只填空着的；「存入模型库」把填好的参数记进自定义层。

### 4.2 预设（preset）

预设 = 一组提供方 + 默认提供方/模型。一个预设可设为默认；用户未指定时用默认预设。
每次修改 `revision+1`。

### 4.3 渲染 `managed.patch.yml`（`models/render.ts`，纯函数，单元测试覆盖）

输入：用户、预设（含提供方）、插件配置片段列表、DSH 版本。输出（示例）：

```yaml
# 由 DSH Hub 生成，请勿手改 —— preset "默认" r7 · 2026-10-12T13:00:00Z
# 用户 u7k2m9x · runtime 0.2.0-rc.2
- id: llm-pi-ai
  config:
    providers:
      hub-relay:
        displayName: 小站中转
        api: openai-completions
        baseURL: https://upstream.example.com/v1
        apiKeyEnv: HUB_MK_HUB_RELAY
        models:
          - id: deepseek-chat
            name: DeepSeek V3
            contextWindow: 131072
- id: agent-default-model
  config:
    provider: hub-relay
    model: deepseek-chat
# —— 默认工作区根（总是输出）——
- id: workspace-controller
  config:
    documentsDirectory: /workspace
# —— 以下为插件配置（按 bundle_order）——
- id: workspace-files
  config: { maxFileBytes: 1073741824, maxBytes: 2097152, maxLines: 5000, maxEntries: 2000 }
```

规则：
- `model_policy = 'free'` 时不输出模型相关条目（用户在 DSH 的模型页自己配）。
- `managed` 时，DSH 设置页对这些字段**不回填、保存被遮蔽**（05 F5）：Hub 的「我的模型」卡片与 DSH 页面里注入的提示都要说明「模型由管理员统一配置」。
- `workspace-controller` 条目若与插件配置里的同 id 冲突，以 Hub 的为准并告警（`config` 整块替换，要写全字段——WP3 先用 `--dump-config` 确认该条目的完整字段）。
- 插件 `config_yaml` 只对**已安装该插件**的用户输出。
- 同一 `id` 出现多次时后者覆盖前者并在渲染结果里给出警告（管理后台预览可见）。
- **保留条目 id**（插件的 `config_yaml` 不得覆盖，渲染时丢弃并告警）：`llm-pi-ai`、`agent-default-model`、`workspace-controller`、`webserver`。
- 输出写入 `managed/managed.patch.yml.tmp` → `rename`（原子替换）；同时写 `manifest.json`。
- 渲染结果变化但密钥 env 未变 → 只需重启 DSH；密钥变化 → `config_hash` 变化 → 重建容器。

## 5. 下发任务（rollout）引擎

### 5.1 流程

```
POST /api/admin/rollouts
  1. 解析 targets → 用户列表（排除 deleted；status=disabled 的也执行，但不启动其实例）
  2. 写期望状态（user_plugins / users.runtime_id / users.model_preset_id）
  3. 建 job + tasks（金丝雀用户排在最前：优先选「管理员自己」与最近活跃用户）
  4. 交给 jobs 引擎：
       阶段 A：串行执行前 canary 个 task；任一失败 → job 暂停（paused），等管理员决定 resume / cancel
       阶段 B：其余 task 以 concurrency 并发；失败比例 > maxFailureRatio → 暂停
  5. 每个 task 调用对应执行器：plugins.installForUser / runtimes.upgradeUser / models.applyForUser
  6. 汇总：全部成功 succeeded；部分失败 partial；被取消 canceled
```

### 5.2 jobs 引擎（WP4，通用基础设施）

```ts
interface JobHandler<P> {
  type: string
  plan(params: P): Promise<{ title: string; tasks: { userId: number | null; payload?: unknown }[] }>
  runTask(ctx: TaskContext, task: TaskRow, params: P): Promise<unknown>   // 抛错 = 失败
}
interface TaskContext { log(line: string): void; signal: AbortSignal; progress(p: { done?: number; total?: number; message?: string }): void }
```

- 状态持久化在 `jobs`/`job_tasks`；Hub 重启后：`running` 的 task 标为 `failed`（error='hub restarted'），job 置 `paused` 等管理员处理。
- 全局并发上限 4 个 task；每用户同一时刻只有一个 task（复用 `withUserLock`）。
- 事件总线：`job`、`task`、`log` 三类事件 → SSE 订阅者；日志块节流 200ms 合并。
- `retry-failed`：失败 task 重置为 pending、`attempt+1`，job 回到 running。
- 导出（`export`）、镜像构建（`runtime.build`）、单实例重建也作为 job 类型复用这套引擎，便于统一展示。

## 6. 数据导出执行器（WP4 `exports/`）

- 读宿主卷，不进容器；不跟随符号链接（符号链接以链接形式写入 ZIP，指向用户根目录之外的直接跳过并记入「跳过清单」）。
- 永远排除：`**/.credentials.yaml`、`**/.env`、`**/node_modules/**`、`**/.pnpm-store/**`、`**/.cache/**`、套接字与设备文件。
- ZIP 内结构：

  ```
  dsh-<username>-20261012-2130/
  ├── README.txt              说明各目录是什么、如何在本机 DSH 里导入会话
  ├── workspace/...
  ├── dsh/sessions/... dsh/attachments/...
  ├── dsh/settings/profile/{package.json,cordis.patch.yml}  dsh/settings/storages/...
  ├── plugins.json            用户自装插件清单（仅勾选「插件清单」时）
  └── manifest.json           导出时间、DSH 版本、文件数、跳过清单
  ```
- 进度：先遍历计数（文件数、字节数）再压缩；`archiver` 的 `progress` 事件节流 500ms 推 SSE。
- 大小保护：遍历阶段累计超过 `exports.maxBytes` → 失败 `EXPORT_TOO_LARGE`，提示「请只勾选部分内容」。
- 打包时持有该用户的读锁，避免与插件安装同时改 profile。
- 过期清理：每小时扫描 `expires_at` 已过的导出，删文件，状态置 `expired`。
